# The refactoring ground truth that already exists

2026-09-13. Until now the tool has been measured against fixtures written here
and questions invented here, graded by graders written here. That is marked
homework. This is a search for an answer key somebody else wrote.

One exists, it is large, and it is human-validated. It is also in the wrong
language and the wrong shape, and both of those are fixable.

## What is out there

**The Refactoring Oracle** (Tsantalis et al., shipped inside RefactoringMiner).
Downloaded and counted directly rather than taken from the paper:

| | |
| --- | --- |
| commits | 550 |
| refactoring instances | 15,754 |
| distinct refactoring types | 102 |
| validated true positive | 11,673 |
| confirmed true positive | 1,252 |
| validated **false** positive | 2,829 |

Validation is by human experts, one to four per instance, cross-checked across
up to six detection tools. RefactoringMiner itself was last pushed on the day
this was written, which is a sharper contrast than it sounds: the TypeScript
indexer this project depends on has had six releases in three years.

The 2,829 false positives are worth as much as the true ones. They are cases
where a tool claimed a refactoring and experts said no, which is the only
material available anywhere for testing precision rather than recall.

**SWE-Refactor.** 1,099 developer-written behaviour-preserving refactorings
across 18 projects, split 922 atomic and 177 compound, each validated by
compilation, test execution and detection tools. The atomic split matters: in
an atomic instance the commit contains one refactoring and nothing else, so the
diff is an uncontaminated answer key.

**RefactorBench.** Synthesised by an LLM rather than drawn from human commits.
Noted and set aside; a benchmark generated by a model is not independent
evidence about a model-driven tool.

## The part that matters: which refactorings this tool is even for

102 types is misleading, because most of them are local edits where finding the
sites is not the hard part. Extract Method has 1,043 validated instances and
poses no call-site problem at all: the work is inside one method.

**5,402 validated instances** where the whole difficulty is enumerating the
affected sites. That is the benchmark for this tool, and it is a very different
number from 15,754.

Pull Up Method, at 292 instances, is exactly "move this common method from
these subclasses to a parent". Extract Interface, at 22, is the nearest single
type to "centralise all usage of an external API behind one service interface",
though that one is really compound and the compound cases are the rarer and
harder ones.

## The two mismatches, and what to do about them

**Shape.** These are *detection* oracles. Each instance says a refactoring
happened between two commits, as prose: `"Extract Method private
destroyDatasetMeta(datasetIndex) extracted from public destroy() in class
core.controller"`. There are no source locations in the record. The fields are
type, description, comment, validation, detectionTools, validators.

That is answering "did a refactoring occur", and the question here is "given an
intent, which sites must change". The bridge is the commit itself. For a
validated instance in an atomic commit, the instruction is the description, the
starting state is the parent commit, and **the locations that commit changed
are the answer key**. Derived rather than handed over, but the validation is
still somebody else's.

**Language.** This is the real problem.

| | commits in the oracle |
| --- | --- |
| Java | 550 |
| Kotlin | present, unexamined |
| JavaScript | **25** |
| TypeScript | none |

The stated priority for this tool is TypeScript, tsx, JavaScript, jsx and
Python. The ground truth is in Java. Twenty-five JavaScript commits is a
rounding error, and their refactorings carry the same prose-only shape.

## What follows

Validating in Java proves the *method*, not the *product*. The question "does a
syntactic candidate set match the set a real refactoring actually touched" is
largely language-independent, and Java is the only place with an answer key at
scale. The tool already parses Java, and scip-java exists for the symbol layer,
so this is not a detour into a language the tool cannot handle.

But it would not have caught the finding that matters most so far. A React
component referenced 21 times across 4 files, where a call-pattern rule returns
zero because every reference is a JSX element, an import clause or a string in
a describe block, is not a shape Java produces. Language-specific failure modes
need a language-specific set, hand-built and small.

So: Java for the recall and precision numbers, across the 5,402 site-finding
instances or a stratified sample of them. A small hand-validated TypeScript set
for the failure modes Java cannot express.

## The boundary that no answer key removes

Dynamic dispatch is not a gap in the tool, it is a property of the problem.
Which implementation runs at a call site is in general a runtime fact, and
deciding it statically is undecidable in the same family as the halting
problem. No oracle fixes this and no layer of the ladder reaches it.

So the target is not 100% recall. It is complete recall over what is statically
decidable, plus an explicit statement of what is not. "612 sites, and 3
dispatch points I cannot resolve, here they are" is a useful answer. "612" is a
dangerous one. The benchmark should score the second sentence as well as the
first, and no existing oracle does that, because detection tools are never
asked to admit what they could not see.
