# codesweep v2: one binary, one parser

Supersedes `plans/v1.md`, whose central structure does not survive measurement.
Everything below was checked against the installed tools rather than reasoned
about, and the checks are named so they can be repeated.

## What v1 got wrong

v1 describes three layers: syntactic enumeration by ast-grep, structural
relationships by `scanner-core`, and symbol resolution by SCIP. The middle
layer does not exist.

`scanner-core`'s `CallSite.callee` holds the raw source text of the call
expression and the crate performs no scope analysis. It matches names. ast-grep
matches names. They are the same layer with different output shapes, and both
are tree-sitter underneath. v1 says as much in passing and then builds a phase
on the distinction anyway.

Demonstrated: ast-grep answers the question phase 3 exists for, today, with no
new code, returning every call site of a name with its file, line and enclosing
function, and correctly skipping an object property of the same name. It does
this across 23 languages where `scanner-core` covers 6.

v1's stated reason for reaching for `scanner-core` is that it exists, builds
clean, and has been unused since December. That is sunk cost, not architecture.

## The decision

codesweep becomes a single Rust binary. ast-grep moves from an external command
to a linked library. `scanner-core` is not used and comes back out.

| Need | v1 | v2 |
|---|---|---|
| Parse many languages without comment or string noise | ast-grep binary, 23 languages | `ast-grep-core`, same engine, in-process |
| Express a rule people can read and version | ast-grep YAML | unchanged, loaded by `ast-grep-config` |
| Enumerate matches deterministically | subprocess and JSON | direct call |
| Stable site identity across reformatting | `hashlib` | `sha2` |
| Persist candidate set and verdicts | `sqlite3`, stdlib | `rusqlite`, bundled |
| Coverage arithmetic and reporting | Python | Rust |
| File discovery honouring ignore rules | shell out to `git ls-files` | the `ignore` crate |
| What calls this, what a change touches | `scanner-core`, 6 languages | ast-grep rules, 23 languages |
| Command surface | `argparse` | `clap` |
| Guidance the model reads | SKILL.md | unchanged |

## Evidence

**The library loads existing rules unchanged.** A spike built against
`ast-grep-core`, `ast-grep-config` and `ast-grep-language` 0.45.3 loaded
`rules/ts-catch-clause.yml` verbatim and returned the same three matches the
binary returns on the same fixture, including the brace form and a clause split
across lines. About forty lines of Rust. No rule migration is needed.

**The result is self-contained.** The installed ast-grep binary, built from
these crates, links only `libiconv` and `libSystem`. No Python, no Node, no
dynamically loaded grammars. Users install one file instead of three, and the
"ast-grep is not on PATH" refusal path disappears because nothing is left to be
missing.

**The language menu becomes a compile-time choice.** `ast-grep-language` exposes
each of 27 grammars as its own cargo feature. v1 wanted a menu and put it at a
layer where it protected nothing; here it decides binary size, which is 44MB
with all of them.

**scss is absent from that feature list**, confirming for a second time, by a
different route, that it must come out of the language map. Pointing it at the
CSS grammar is not a fix: on a six-line SCSS file the CSS grammar returns two of
three declarations and drops the one using a Sass variable, silently.

## Why not stay on Python

The Python CLI is stdlib-only and has no dependencies, so the usual argument
against it does not apply. Two things decide it anyway. Keeping Python while
adding any Rust gives two toolchains and two parser stacks for one job. And the
plugin currently ships guidance with nothing executable behind it, so packaging
has to be solved regardless; solving it once for a single artifact is simpler
than solving it for a script plus a binary plus an external dependency.

The cost is real and is not hidden: about 1100 lines to port with 103 tests
behind them, four platform builds or a Rust toolchain on the user's machine, and
a plugin that carries a binary rather than a script.

## Consequences for the backlog

- The vendored `crates/scanner-core` comes out. The tsx defect fixed in it was
  real and the fix was correct; the crate is simply not needed here.
- The caller and change-impact commands become rule templates run in-process,
  not a separate indexer with its own binary.
- Removing scss stands, now with two independent reasons.
- The eval work is unaffected in substance. Its packaging changes, because the
  plugin must carry a binary.
- SCIP remains the only real second layer, and remains deferred.

## The defect that outranks all of this

The plugin ships SKILL.md and nothing else. The skill issues eight `codesweep`
commands and its Requirements section names only ast-grep. Anyone installing the
plugin without running `install.sh` gets a protocol for a command they do not
have. Observed directly in an eval run, where the agent noticed, said so, and
improvised with ast-grep by hand.

Fix that first, under either architecture: ship the executable with the plugin,
and have the skill verify it resolves before step one, the way it already treats
a missing ast-grep.

## The resolution layer, decided

v1 deferred SCIP with a one-line reason. This is the decided shape, arrived at
by measurement during the session that produced this document.

### SCIP, not live language servers

They are not alternatives. SCIP is a format for resolved code intelligence and
the language server protocol is a way of getting it out of a running process;
`lsp-to-scip` exists precisely to bridge one to the other. For resweep the index
wins on three counts: queries are cheap and offline where resweep asks thousands
rather than a handful, an index is a citable artefact that can be stored and
diffed, and it survives the session where a running server does not. Sourcegraph
reached the same conclusion from the other direction and deprecated language
server support for code intelligence in favour of an index.

Language servers keep one job: producing an index for languages with no native
indexer. That is most of the tail, so the bridge matters, but it is plumbing
behind the index rather than a second mode.

### Nothing is bundled, and nothing installs mid-audit

Indexers are per language and are not present by default. Measured on a
well-equipped machine: four language servers on PATH, all of them side effects
of having Rust, Python and Xcode installed, none deliberately installed, and
none for TypeScript, which is the language this project is written in and
audits. Nine more sit inside editor extensions where a terminal cannot reach
them. So detection alone would mostly report that no route exists.

The answer is to install, at install time, with consent, through
`resweep setup` run inside the target project. It scans the project the way the
census already scans it, honouring ignore rules, proposes the indexers for the
languages actually present, and installs the ones the operator accepts. Globally
by default, since that works across repositories. Never into the project's
manifest unless asked, because that is a commit.

Two rules follow.

An audit never stops to install anything. Every run either has full capability
or degrades with a clear message, and which one is known before it starts.

A language with no resolution route degrades the completeness claim rather than
falling back quietly. This has an exact precedent: the census already reports
every source extension in scope that no rule can reach and refuses to call the
sweep complete while any remain. The new warning is the same shape one layer up,
naming the language, the consequence, and the one command that closes it. That
warning is also the top-up path when a project turns up with a language the
operator did not select.

`resweep setup` is a command rather than a step inside the installer, because
the installer runs from resweep's own clone and scanning that would seed exactly
the wrong languages with total confidence.

### Where the pieces live

| Thing | Where | Why |
|---|---|---|
| the indexer | project-local first, then user-global; version reported | a team can pin one, an individual installs once |
| the invitation | driven by a scan of the target project | offering seven languages to a project with two is how a setup step gets skipped |
| the index | user cache keyed by repository and commit | minutes to build, so not per session; large and churning, so not in the repository |
| the ledger | per-session temporary directory, unchanged | seconds to rebuild, nothing worth persisting |

### What has a future

Checked rather than assumed, because building on abandoned tooling is a real
risk here.

| Piece | Signal | Verdict |
|---|---|---|
| tree-sitter | everything below rests on it | alive |
| ast-grep | 0.45.3, active | alive |
| SCIP | independent governance since March 2026, steering committee including Uber and Meta engineers, repositories active to July 2026, emitted by rust-analyzer, Searchfox and Glean | alive, and safer than when one vendor owned it |
| `@sourcegraph/scip-typescript` | 0.4.0 in October 2025, six releases in three years | maintained, slow, and the weakest link in the chain |
| the language server protocol | universal; `typescript-language-server` published August 2026 | alive |
| `lsp-to-scip` | Intuit's infigraph, 2.0.0 | promising, unproven |
| LSIF | superseded by SCIP | dead |
| stack-graphs | archived September 2025 | dead |

The TypeScript indexer is the risk. It is the one resweep would depend on first
and it is on maintenance rather than investment. If it stalls the fallback is
bridging a language server, which is why the bridge is worth keeping in the
design even though it is not the primary route.

### The caveat that does not go away

An index needs a project that resolves. None of this helps the half-refactored
tree with dependencies uninstalled, which is exactly when someone is asking what
a change would touch. This raises the ceiling for healthy projects and changes
nothing for the case v1 was most excited about, and that is the honest reason to
keep it behind the two changes that need nothing installed.

## Rename: codesweep is taken

`codesweep` is HCL AppScan's free security scanner, with a VS Code extension and
a GitHub action, and separately codesweep.ai, which sells guardrails for coding
agents and is close enough to this pitch to be a problem. There is no collision
with Claude Code itself: zero occurrences in the binary and nothing in the
plugin marketplaces, so the one on this machine is our own symlink.

The name is `resweep`, short for refactor sweep. Free on npm and crates.io.

One caveat to hold: shape-defined refactors are in scope and symbol-defined ones
are not, so the name promises slightly more than the tool delivers. The
motivating example, replacing scattered binding access with a single composition
step, is shape-defined, so it fits the case that matters.

The rename is not mechanical. The skill's description contains the word, and
that description is the trigger, measured by a probe set that caught a defect in
every one of five earlier rounds. Renaming means re-running the probe round.
